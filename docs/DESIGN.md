# 設計

ML-Studio の設計と決まりをまとめる. まだやっていないことは [TODO.md](../TODO.md) に置く.

## 1. 役割と位置づけ

「機械学習を全て GUI 上で行う」アプリの殻. 5 つの段階のアプリを 1 つのアプリにまとめ, 1 つのコマンドと 1 つのポートで起動する.

| 段階 | アプリ | 経路の頭 (画面) | 経路の頭 (API) |
| --- | --- | --- | --- |
| 問題の設定 | ML-Pathfinder | `/problem` | `/api/problem` |
| データの分析 | ML-Fathom | `/data` | `/api/data` |
| モデルの作成・選定 | ML-CreateArchitecture | `/model` | `/api/model` |
| 学習・評価 | ML-Dashboard | `/train` | `/api/train` |
| 推論 | ML-Provide | `/infer` | `/api/infer` |

- 殻が持つのは, 起動, 起動ごとのトークンと Origin と Host の確かめ, 各アプリのバックエンドと画面を載せること, 段階の並び, 共通の部品, プロジェクトの選び方だけ. 各段階の画面と API, 段階のライブラリを使う仕組みは各アプリに置く (段階ごとの中身を 1 か所で直せるようにするため)
- 各アプリは単独でも今まで通り動く. 殻は各アプリが公開する形 (2 の節) だけを使い, 各アプリの中の作りに頼らない (単独の起動と殻の下の起動で同じ API と画面を使うため)
- 段階をまたぐ通しの確かめ (5 つの段階を 1 つのアプリで通す結合テスト) はこのリポジトリが持つ. 各アプリのテストは単独の起動を確かめる

## 2. 使うアプリと約束

5 つのアプリを submodule で持つ (各アプリの版を殻の側で決めて, 組み合わせを再現できるようにするため). 各アプリに求める約束は次の 2 つ.

### バックエンド: `create_api`

各アプリのパッケージ (`ml_pathfinder`, `ml_fathom`, `ml_createarchitecture`, `ml_dashboard`, `ml_provide`) の `app` モジュールが, 次の形の関数を公開する.

```python
def create_api(
    data_dir: Optional[Path] = None, *,
    problems_dir: Optional[Path] = None, ...  # アプリ固有の引数
) -> FastAPI: ...
```

| 引数 | 意味 |
| --- | --- |
| `data_dir` | アプリの置き場. None の場合は各アプリの既定 (環境変数かホームの下) |
| `problems_dir` | 問題の設定の置き場 (`<識別子>/problem.yaml` が並ぶディレクトリ). None の場合は各アプリの今の既定. 決めた値 (既定も含む) は `app.state.problems_dir` に置き, 問題の設定を読む所は全てここから取る (殻が ML-Pathfinder の決めた場所を読んで他に渡せるようにするため) |
| アプリ固有の引数 | 起動時に登録簿に入れる自作の部品. ML-CreateArchitecture は `modules`, ML-Provide は `procedures` と `units` |

返す FastAPI のアプリは次を満たす.

| 決まり | 理由 |
| --- | --- |
| router は頭なし (`APIRouter()`) で作る. 経路は mount の頭を除いた形 (例 `/problems`) | Starlette は mount の頭を除いた経路で照合するので, 頭を殻が決められる |
| トークン, Origin, Host の確かめ, `/api/auth`, 画面の配信を付けない | 殻の下で確かめが重ならないように, 殻が 1 つだけ持つ |
| `docs_url` と `openapi_url` を None にする | API の一覧を外に見せない |
| `app.state` (置き場など) と例外ハンドラは今のまま持つ | mount した sub-app の中では `request.app` が sub-app を指すので, 今の取り方のまま動く |
| lifespan と startup, shutdown の処理を使わず, 要る準備は `create_api` の中で済ませる | mount した sub-app の lifespan は Starlette が動かさないため |
| モジュールの読み込みで app を作らず, 呼ぶたびに新しいアプリを返す | テストと殻で別の置き場を渡せるようにする |
| 起動を止める場合 (読めない自作の部品など) は `ValueError` (かその子) を, 利用者に見せる日本語の理由を付けて出す. 同じプロセスの他のアプリの状態 (登録簿の部品など) は消さない | 殻の起動が理由の 1 行を出して終われるように, 型を 1 つにそろえる |

単独の `create_app` は, 確かめと `/api/auth` と画面の配信を付けた外側のアプリに, `create_api(...)` を `/api` の下で加える (今の経路 `/api/...` と振る舞いを保つため).

### 画面: 根の部品

各アプリの画面のパッケージが, 段階の画面の根の部品を公開する. 殻は 1 つの画面 (pnpm workspace) に各アプリの部品を取り込む. 取り込みは, 殻の submodule の中の各アプリの画面のパッケージを workspace に加え, そのパッケージの公開する根の部品と CSS を import する形にする (各アプリのビルド済みの画面に頼らず, 1 つのビルドにまとめるため).

| props | 型 | 意味 |
| --- | --- | --- |
| `basename` | `string` | 画面の経路の頭 (例 `/problem`). 部品の中の経路と移動先はこの下に置く. 単独では `""` |
| `apiBase` | `string` | API の頭 (例 `/api/problem`). API の呼び出しは全てこの下に送る. 単独では `/api` |
| `project` | `string \| null` | 殻で選んだプロジェクト (5 の節). null の場合は選んでいない |
| `onProjectChange` | `(project: string \| null) => void` | 部品の中でプロジェクトを替えたとき (ML-Pathfinder で問題の設定を新しく作った, 開いた, 消したときなど) に呼ぶ. 殻は受け取った値を選んだプロジェクトにする |
| `onProjectsChange` | `() => void` | プロジェクトの一覧が変わったとき (作った, 名前を変えた, 消した) に呼ぶ. 殻は一覧を読み直す |
| `embedded` | `boolean` | true の場合はアプリの名前と明暗の切り替えを出さない (殻の上の帯が持つため). 段階の中の移動 (左の欄の項目, 節の並びなど) は今のまま部品の中に出す. 単独では false |

- 部品は自分の TanStack Query の client を持ち, 画面の中に経路を持つ場合は自分の react-router のルーター (`BrowserRouter` か `createBrowserRouter` に `basename` を渡したもの) も持つ (各アプリの中の画面の作りを殻に出さないため). 殻は react-router を使わない (ルーターが入れ子になると react-router が例外を出すため)
- 部品の中の移動は `basename` の下に留め, 段階をまたぐ移動はしない (段階の切り替えは殻の段階の並びだけが行うため)
- 選んだプロジェクトは props で受け取り, 部品の中の経路や検索パラメータを殻の選びの元にしない (部品の中の移動で選びが落ちないようにするため). 単独では部品が今まで通り自分で選ぶ
- 画面の中で根から始まる絶対パス (`/favicon.svg`, `<a href="/">` など) を使わない. 画像は import してビルドに含め, 段階の頭へ戻る移動は `basename` の下の `Link` にする (殻の下では根が殻の画面を指すため)
- 明暗は殻と同じく `html` 要素のクラス `dark` と `localStorage` の `theme` で持ち, `embedded` のときは読むだけにする (殻の切り替えが全ての段階に効くようにするため)
- 段階に固有の CSS (各アプリの `index.css` のうち, Tailwind の読み込みと色のトークン以外) は, 根の部品と別の CSS として公開する
- トークンは httponly の Cookie で送り, 画面の JS は扱わない (殻と単独で同じ)
- 根の部品は自分の範囲の要素に `data-stage-root` を付ける (箱を作らない `display: contents` でよい). `window` や `document` で聞くキーの操作は, キーの target がこの範囲の中か `body` のときだけ扱う (R9). メニューや対話の枠を `createPortal` で出すときは, 出す先もこの範囲の中にする (範囲の外に出すと, その中のキーを扱えなくなるため)
- 保存していない書きかけは下書きに残し, 部品が外されるときと `project` が替わるときに待たずに書く (R10). 殻は段階の移動を止めず, 確かめの窓も出さない (部品が殻に移動を止めさせる口を持たず, 段階を自由に行き来できるようにするため)

## 3. 画面

殻の画面は 1 つのページで, 上に共通の帯, その下に選んだ段階の根の部品を置く.

| 部分 | 内容 |
| --- | --- |
| 上の帯 | アプリの名前, プロジェクトの欄, 段階の並び (問題の設定 → データの分析 → モデルの作成・選定 → 学習・評価 → 推論), 明暗の切り替え |
| 段階の画面 | 経路の頭 (`/problem` など) に合う段階の根の部品. `basename`, `apiBase`, 選んだ `project`, `onProjectChange`, `onProjectsChange`, `embedded` (true) を渡す |

- 段階は location の経路の最初の区切り (`/problem` など) で選ぶ. `/` と知らない頭は `/problem` に移す (最初の段階から始めるため)
- 段階の並びを押すと, 殻が `history.pushState` で経路を段階の頭に替え, 段階ごとに別の `key` を付けて根の部品を作り直す (部品のルーターが新しい経路を読み直すようにするため). 戻ると進むで段階をまたいだときは, 殻が `popstate` で知って同じように作り直す
- 段階の中の移動は経路の頭を変えないので, 殻は知らなくてよい (段階を選ぶのに頭しか使わないため)
- 段階の根の部品は段階ごとに分けたチャンクにあり, その段階を初めて開くときに読む (8 の節). 読む間は上の帯を出したまま, 段階の場所に読み込み中と出す (`role="status"`. 帯の操作を待たせず, 何を待っているかを見せるため)
- 段階の画面を読み込めないとき (ネットワークの誤り, 殻の画面を作り直した後に古いファイルの名前を読んだときなど) と, 段階の部品が描く途中で例外を出したときは, 上の帯を出したまま, 段階の場所に出せないことと理由と再読み込みのボタンを出す (`role="alert"`. 1 つの段階の誤りで殻の全体を消さないため). 別の段階に移るときと今の段階を押し直したときに出し直す (段階の中の戻ると進むでは出し直さない). 読めなかった段階は React が失敗を覚えて同じ誤りを返すので, ページの再読み込みで読み直す (作り直した後の新しいファイルの名前も再読み込みで読めるため)
- 段階の並びはいつでも押せ, 段階を移っても選んだプロジェクトを引き継ぐ (前の段階に戻って直せるようにするため)
- 今の段階を押し直すと, 履歴を増やさずに段階の頭から部品を作り直す (段階の中で迷ったときに最初へ戻れるようにするため). 選んだプロジェクトがあれば, 作り直した部品がそれを開く
- 選んだプロジェクトは殻が状態として持ち, 根の部品に props で渡す. 再読み込みで保つため, `localStorage` の `studio-project` にも残す (読めない環境では選んでいない形で始める). 上の帯の欄で選んだときと, 部品が `onProjectChange` を呼んだときに替える
- 明暗は殻が持ち, `html` 要素のクラス `dark` と `localStorage` の `theme` に置く (5 つのアプリと同じ場所にして, 段階の部品がそのまま読めるようにするため)
- 殻の画面のビルドは 1 つで, Tailwind と色のトークンを 1 度だけ読み込み, 5 つのアプリの画面のソースを Tailwind の探す先に加え, 各アプリが公開する段階に固有の CSS を取り込む (同じ規則を何度も読み込まないため). `favicon.svg` は殻が配る
- 段階に固有の CSS は, 段階の部品を分けて読んでも殻の入口 (`main.tsx`) で全ての段階の分を読む (小さく, 規則が段階の要素 (`.react-flow` など) に限られていて段階をまたいで混ざっても困らず, 段階を開いたときに見た目が遅れて替わらないため). 根の部品が自分で import する CSS (ML-CreateArchitecture の React Flow の CSS) は段階のチャンクと一緒に読まれ, 部品を出す前に読み終わる

## 4. API

殻は 1 つの FastAPI のアプリに, 各アプリの `create_api` を 1 の節の表の経路の頭で mount する.

| 経路 | 内容 |
| --- | --- |
| `GET /api/auth?token=` | トークンを確かめて Cookie に置き, `/` に 303 で移す. 合わなければ 401 (5 つのアプリと同じ) |
| `/api/problem/...` など | 各アプリの API (経路の頭を除いた形は各アプリの単独の `/api/...` と同じ) |
| `/assets/...`, その他 | 殻の画面のファイル. `/api` の下以外の他の経路は `index.html` を返す (画面の中の経路のため). `/api` の下で合わない経路は 404 (API の呼び間違いを画面の HTML で隠さないため) |

- プロジェクトの欄の一覧は, 問題の設定の識別子と名前を問題の設定の段階の API (`GET /api/problem/problems`) から読み, 殻は問題の設定の形を読まない (形を ML-Pathfinder だけが知るようにするため)
- 殻のアプリも `docs_url` と `openapi_url` を None にする

## 5. 用語

| 用語 | 意味 |
| --- | --- |
| 殻 | このリポジトリのアプリ. 5 つの段階のアプリを載せる |
| 段階 | 問題の設定, データの分析, モデルの作成・選定, 学習・評価, 推論の 5 つ. それぞれを 1 つのアプリが受け持つ |
| 段階の鍵 | 経路の頭に使う語. `problem`, `data`, `model`, `train`, `infer` |
| プロジェクト | 殻で選ぶ 1 つの問題の設定の識別子 (ML-Pathfinder の問題の設定の置き場の `<識別子>`). 全ての段階が同じ値を受け取る. `problem.yaml` の中の学習のプロジェクトの記録や, 各アプリの中のプロジェクト (学習・評価の段階の学習のプロジェクトなど) とは別のもので, 各段階が自分の扱う対象をこの識別子にどう対応させるかは各アプリが決める |
| `create_api` | 各アプリが公開する, 確かめと画面の配信を持たない API のアプリを作る関数 |
| 根の部品 | 各アプリが公開する, 段階の画面の一番外の React の部品 |

## 6. 置き場

殻はサーバーの側に自分の置き場を持たない (選んだプロジェクトと明暗は画面の `localStorage` に持つ).

- 各アプリの置き場 (`data_dir`) は渡さず, 各アプリの既定 (環境変数かホームの下) のままにする (単独で作ったものを殻でも, 殻で作ったものを単独でも開けるようにするため). ML-Pathfinder は `ML_PATHFINDER_HOME` か `~/.ml-pathfinder/`, ML-Fathom は `ML_FATHOM_HOME` か `~/.ml-fathom/`, ML-CreateArchitecture は `ML_CREATEARCHITECTURE_HOME` か `~/.ml-createarchitecture/`, ML-Dashboard は `ML_DASHBOARD_HOME` か `~/.ml-dashboard/`, ML-Provide は `ML_PROVIDE_HOME` か `~/.ml-provide/`. ML-CreateArchitecture の自作の部品 (`modules`) と ML-Provide の自作の部品と手順 (`units`, `procedures`) も渡さず, その既定 (起動の設定 `ML_CREATEARCHITECTURE_MODULES`, `ML_PROVIDE_UNITS`, `ML_PROVIDE_PROCEDURES`) のままにする (単独と同じ設定で同じ部品を使えるようにするため). 殻は ML-CreateArchitecture の extra のうち `project` だけを入れるので, 外部のライブラリの部品のうち, 他の段階のために殻の環境に入るもの (推論の段階が使う torchvision) の部品だけが使え, 他 (huggingface, timm など) は殻では使えず, 部品の一覧で使えないと出る (殻の 1 つの環境を軽く保つため)
- 問題の設定の置き場は, 殻が ML-Pathfinder の `create_api()` を先に呼び, その `app.state.problems_dir` を他の 4 つのアプリの `create_api` に `problems_dir` として渡す (場所を決めるのを ML-Pathfinder だけにし, 殻が中の作りに頼らず, アプリごとに場所が食い違わないようにするため)

## 7. 安全

既定では `127.0.0.1` だけで待ち受ける (他のホストを指定すると警告を出す). トークンを持つ人は手元のファイルを読み書きでき, 学習・評価の段階では任意のディレクトリのプロジェクトを登録して, 選んだ Python で学習を起動し, 環境に依存を入れられる (手元でプロセスを起動できる) ので, トークンは他の人に渡さず, 他のホストで待ち受けるときは信頼できる網の中に限る.

- 起動ごとのトークン (環境変数 `ML_STUDIO_TOKEN`, 無ければランダムに作る) を, Cookie (`ml_studio_token_<印>`. 印はトークンから作り, 同じ端末の別の起動と重ならないようにする) かヘッダー `x-studio-token` で受け取り, `/api` の下の全ての要求で確かめる. 外すのは `GET /api/auth` だけで, 他のメソッドの `/api/auth` も確かめる (トークンを受け取る入口だけを開けるため). 合わなければ 401. 比べるときは時間で推測されない比べ方を使う
- 書き込みの要求 (GET, HEAD, OPTIONS 以外) は, Origin が接続先と違えば断る (他のサイトからの書き込みを防ぐため)
- 受け付けるホスト名を決め (既定は `127.0.0.1` と `localhost`), 他のホスト名での接続を断る (DNS の付け替えを防ぐため). `--host` に名前かアドレスを渡したときはそれも受け付け (出した URL をそのまま開けるようにするため), さらに足すときは `--allowed-host` (何度も渡せる) で足す. IPv6 のアドレスでの接続は受け付けない (受け付ける形を決めていないため)
- この 3 つの確かめは殻のアプリだけが持ち, mount した各アプリの API は持たない (確かめが重なると, トークンの名前や Cookie が段階ごとに分かれて 1 つの画面から呼べないため)

## 8. 起動と載せ方

- 起動は 1 つのコマンド `ml-studio` (`--host`, `--port`, `--allowed-host`). 各アプリの設定は各アプリの環境変数のまま (6 の節). 起動するとトークン付きの `/api/auth` の URL を出す. 段階のアプリが起動を止めた場合 (読めない自作の部品など) は, 理由を出して終わる
- 1 つのプロセス (worker 1 つ) で動かす. 学習・評価の段階のジョブの管理と, 起動時に部品を入れる登録簿がプロセスの中の状態のため
- 学習・評価の段階のアプリは 1 つのプロセスで 1 度だけ作り, 同じ置き場を 2 つのアプリに渡さない (ジョブのプロセスとロックをアプリごとに持つため). 学習のジョブは登録した学習のプロジェクトの Python の子プロセスとして動き, 学習のまとまりと環境の準備は殻のプロセスの中のスレッドで進む
- 自作の部品の登録簿 (ML-ModelControl の登録簿) はプロセスに 1 つで, 部品を入れるアプリ (モデルの作成・選定の段階, 推論の段階) の間で共有になる. 同じモジュールは 1 度だけ入り, 2 つのアプリの起動の設定に同じモジュールを書いてよい (殻のテストで, 両方に書いて起動し, モデルの作成・選定の段階で確かめて保存した定義から推論の段階で一式を作って推論できることを確かめる). 同じ部品の名前を別々のモジュールで宣言すると, 後から `create_api` を呼んだアプリ (段階の並びの後ろ) が起動を止める. モデルの作成・選定の段階の部品の一覧は登録簿の全体を出すので, 他のアプリが入れた部品も出る
- 殻は 5 つのアプリの `create_api` を段階の並びの順に 1 度ずつ呼んで mount する. ML-Pathfinder を先に呼び, その問題の設定の置き場を他に渡す (6 の節). 各アプリの例外ハンドラ, 子プロセス, スレッドは mount した sub-app の中でそのまま動く
- 各アプリの画面は殻の画面のビルドに取り込み, 各アプリのビルド済みの画面 (`static/`) は使わない (共通の部品と 1 つのビルドにまとめるため)

### 載せた段階と依存

| 段階 | アプリ (submodule) | アプリが submodule で持つライブラリ |
| --- | --- | --- |
| 問題の設定 | `ML-Pathfinder/` | ML-Quest |
| データの分析 | `ML-Fathom/` | ML-EDA, ML-Quest |
| モデルの作成・選定 | `ML-CreateArchitecture/` | ML-ModelControl (ML-EDA と ML-Quest は git の依存. extra `project`) |
| 学習・評価 | `ML-Dashboard/` | ML-Found, ML-Quest (extra `problem`) |
| 推論 | `ML-Provide/` | ML-Inference, ML-Quest (ML-EDA と ML-ModelControl は git の依存. ML-Inference も ML-EDA と ML-ModelControl を git の URL で求める) |

- submodule の中の submodule も取る (`git submodule update --init --recursive`. CI の checkout も `submodules: recursive`). 各アプリがライブラリを submodule で持ち, 殻はそれを使うため
- バックエンドは 1 つの Python の環境 (uv) に, 各アプリのパッケージとライブラリを submodule から editable で入れる (`backend/pyproject.toml` の `tool.uv.sources`). アプリが git の依存で求めるライブラリ (ML-CreateArchitecture の ML-EDA と ML-Quest, ML-Provide の ML-EDA と ML-ModelControl) と, ライブラリが `dependencies` に git の URL で求めるライブラリ (ML-Inference の ML-EDA と ML-ModelControl) も, 下の上書きで殻の 1 つの求め方に置き換える (上書きしないと, submodule の求めと URL がぶつかって解けないため). PyTorch と torchvision は ML-CreateArchitecture, ML-Dashboard, ML-Provide と同じく Linux では CUDA の無い版の index から取る (index はアプリの pyproject.toml のものが効かず, 殻の pyproject.toml に書く要があるため. CI の時間と大きさを抑えるため)
- 同じライブラリを 2 つ以上のアプリが使う場合は, 殻の `tool.uv.override-dependencies` で 1 つの求め方に上書きし, `tool.uv.sources` でアプリの submodule のうち 1 つ (今は ML-Fathom の ML-EDA と ML-Quest, ML-CreateArchitecture の ML-ModelControl) を指す (1 つの環境には 1 つの版しか入らず, アプリごとの submodule の版や git の版の求めがぶつかるため). 各アプリの submodule の版は下の「共通のライブラリの版」にそろえる (R8). 上書きは extra ごと置き換えるので, 各アプリが使う extra を全て書く. そろえた版で各段階の API が動くことは, CI で殻の環境のまま各アプリのテストを流して確かめる (殻のテストと通しの確かめは各段階の API の一部しか通らないため)
- 画面は 1 つの pnpm workspace (`frontend/pnpm-workspace.yaml`) に各アプリの画面のパッケージを加え, 共通の依存 (react, react-router, TanStack Query など) を 1 つの版に解く. react と react-dom は vite の `dedupe` でも 1 つにする (2 つ読むとフックが動かないため). 開発用のサーバーが submodule の画面のソースを配れるよう, vite の `server.fs.allow` に各アプリの画面のディレクトリを加える
- 画面のビルドは殻の入口 (上の帯と段階の並び) と段階ごとのチャンクに分け, 段階の根の部品は `React.lazy` と動的な `import()` で, その段階を開いたときに読む (図の部品やキャンバスの部品で段階の部品の全体が 2.7 MB 近くあり, 1 つにまとめると段階を足すたびに最初の読み込みが重くなり, 段階を足すと大きさの閾値も超えるため). 段階の間で共通の依存 (react-router, TanStack Query など) は Vite が別のチャンクに分けて使い回す. 大きさの警告の閾値は 2500 kB のままにし, 上げない. 段階を足すときも同じ形で分ける

### 共通のライブラリの版

2 つ以上のアプリが使う (submodule で持つか, git の依存で持つか, 持つライブラリを通して求める) ライブラリの版 (コミット) を殻が決め, そのライブラリを submodule か git の依存 (`backend/pyproject.toml` の `tool.uv.sources` の `git`. 版は `backend/uv.lock` が決める) で直に持つアプリはその版に合わせる (R8). git の依存は `tool.uv.sources` で書き, `dependencies` に `@ git+...` の形で書かない (確かめが sources から git の依存を探すため). 殻の木の中の同じライブラリは 1 つの版にする. この表が版を書く唯一の場所で, 殻の確かめもこの表を読む (版を 2 か所に書くと食い違うため).

| ライブラリ | 版 | 使うアプリ |
| --- | --- | --- |
| ML-Quest | `8ec1524` | ML-Pathfinder (submodule), ML-Fathom (submodule), ML-CreateArchitecture (git の依存), ML-Dashboard (submodule), ML-Provide (submodule) |
| ML-EDA | `2a7782f` | ML-Fathom (submodule), ML-CreateArchitecture (git の依存), ML-Provide (git の依存. ML-Inference と ML-Quest を通しても), ML-Pathfinder (ML-Quest を通して) |
| ML-ModelControl | `24d3720` | ML-CreateArchitecture (submodule), ML-Provide (git の依存. ML-Inference を通しても) |

- 殻の木の中の同じライブラリの submodule と, 載せた各アプリが git の依存で直に持つライブラリの lock の版が, 全てこの表の版であることを, CI で `scripts/check_versions.py` が表を読んで確かめる (アプリの submodule を上げ忘れると, 殻の 1 つの環境のどの版で動いているかが分からなくなるため)
- 版はライブラリの `main` のコミットから選ぶ. 上げるときは, 先にこの表を直してから各アプリに頼み, 全てのアプリが合わせた後に, 殻が持つ各アプリの submodule の版を上げる (アプリごとに上げると, 殻の 1 つの環境で版がぶつかるため)
- 新しい共通のライブラリ (ML-Found, ML-Inference など) を使うアプリが 2 つ以上になったら, そのアプリを殻に載せる前に, この表に足す (載せる前にアプリが表の版に合わせられるようにするため)
- ライブラリが git の版で求める他のライブラリ (ML-Quest の `ml-eda` の求めなど) は, 殻では上の `override-dependencies` で表の版に置き換わる. 各アプリの単独の起動はその求めのままでよい

## 9. 各アプリへの要求と進め方

殻は 5 つのアプリへの要求を決め, 各アプリはその要求に合わせて形を作る (各アプリが統合を見ずに機能を広げると, 1 つのアプリにまとめにくくなるため). 要求の一覧はこの節が持ち, 各アプリの TODO.md の高と中は, ここの要求に結び付く項目を先に置く. 統合に結び付かない機能の拡張は, 統合が済むまで各アプリの低か条件待ちに置く.

| 要求 | 中身 (2 の節) | 確かめ方 |
| --- | --- | --- |
| R1. `create_api` | 確かめと画面の配信を持たない API のアプリを返す関数を公開する. 準備は `create_api` の中で済ませ (lifespan を使わない), 呼ぶたびに新しいアプリを返す. 単独の `create_app` はその外側に確かめを付けて `/api` の下に加える | 単独の起動の確かめ (401, 403, 400, 画面の配信) が今と同じで, 別の頭に mount した `create_api` が確かめ無しで動き, 2 度呼んでも誤りにならないテストが通る |
| R2. `problems_dir` | `create_api` の `problems_dir` で問題の設定の置き場を受け取り, `app.state.problems_dir` から読む | 渡した置き場の問題の設定を読むテストが通る |
| R3. 根の部品 | `basename`, `apiBase`, `project`, `onProjectChange`, `onProjectsChange`, `embedded` を受け取る段階の画面の部品を公開する | 殻の画面に取り込み, 段階の頭の下で画面と API の呼び出しが動く |
| R4. 根からの絶対パスを使わない | 画面のソース (`src`) で根から始まる絶対パスを使わない. 移動はルーターの `basename` の下にし, 画像は import する. `index.html` は殻が自分のものを使うので, 各アプリの `index.html` の `/favicon.svg` は単独の起動のために残してよい | 殻の下で段階の画面から殻の画面へ移らない |
| R5. 明暗 | `html` の `dark` と `localStorage` の `theme` で持ち, `embedded` では読むだけにし, `html` のクラスの変化を見て読み直す (殻が切り替えたときに, 色を読むグラフなども替わるようにするため) | 殻の切り替えが段階の画面に効く |
| R6. 殻のプロジェクト | `project` を受け取り, 各段階の扱う対象を選ぶ (問題の設定の段階は開く, 他の段階はその問題の設定から始める). 受け取った値と同じプロジェクトを開いたときは `onProjectChange` を呼ばない (殻と部品の間で知らせが行き来し続けないため) | 殻の欄で選んだプロジェクトを段階の画面が開く |
| R7. 段階に固有の CSS | 根の部品と別に, 段階に固有の CSS (Tailwind の読み込みと色のトークン以外) を公開する | 殻の 1 つのビルドに取り込んだ段階の画面の見た目が, 単独と同じ |
| R8. 共通のライブラリの版 | 2 つ以上のアプリが使うライブラリを submodule か git の依存で直に持つ場合は, 8 の節の「共通のライブラリの版」の版に submodule か lock を合わせる (殻の 1 つの環境に 1 つの版しか入らず, 版がずれると, あるアプリのテストを通った版で別のアプリが動くか分からないため). 版を上げたら, 自分のテストをその版で通す. 中身は 8 の節 | 自分の submodule と lock の版が表と同じで, 自分のテストが通る. 殻の側では, 殻の木の中の同じライブラリの submodule と載せたアプリの lock が全て表の版で, 殻の CI で各アプリのテストが殻の環境のまま通る |
| R9. 部品の外のキーを扱わない | `window` や `document` で聞くキーの操作 (元に戻す, 保存, 消すなど. 外部のライブラリが聞くものも含む) は, 段階の画面の部品の範囲の中 (根の部品が付ける `data-stage-root` の要素の中) と, どこにも focus が無い (`body`) ときだけ扱う (殻の上の帯の欄やボタンで押したキーで, 段階の中身を変えないため). 中身は 2 の節 | 殻の上の帯に focus があるときのキーで, 段階の中身が変わらない. 単独の起動のキーの操作は変わらない |
| R10. 離れるときに書きかけを捨てない | 保存していない書きかけを持つ画面は, 書きかけを必ず下書き (ブラウザの保存先など) に残し, 部品が外されるとき (殻の中で段階を移る, 同じ段階を押し直す) と殻の `project` が替わるときに, 待たずに書く. 部品が次に開いたときに下書きを戻せるようにする (殻の中の移動はページを閉じないので `beforeunload` の確かめが出ず, 部品は移動を止められないため). 中身は 2 の節 | 書きかけのまま段階を移るか殻でプロジェクトを替えて戻ると, 書きかけが下書きから戻せる |

- 進め方は縦に 1 つずつ通す. まず問題の設定の段階 (ML-Pathfinder) だけを殻に載せて, 1 つのコマンドで画面が開き API が動くところまで通し, 通った形を手本に段階の並びの順で残りを載せる (5 つを同時に作り替えると, 要求の誤りが 5 か所に広がるため)
- 要求を足すか変えるときは, 先にこの節を直してから各アプリに頼む (各アプリが別々に決めると, また形が分かれるため)
- 各アプリは要求を満たした後も単独で今まで通り動く (段階ごとに作り直せるという全体の方針を崩さないため)
