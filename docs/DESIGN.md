# 設計

ML-Studio の設計と決まりをまとめる. まだやっていないことは [TODO.md](../TODO.md) に置く.

## 1. 役割と位置づけ

「機械学習を全て GUI 上で行う」アプリの殻. 5 つの段階のアプリを 1 つのアプリにまとめ, 1 つのコマンドと 1 つのポートで起動する.

| 段階 | アプリ | 経路の頭 (画面) | 経路の頭 (API) |
| --- | --- | --- | --- |
| 問題の設定 | ML-Pathfinder | `/problem` | `/api/problem` |
| データの分析 | ML-Fathom | `/data` | `/api/data` |
| モデルの作成・選定 | ML-CreateArchitecture | `/model` | `/api/model` |
| 学習・評価 | ML-Dashboard | `/train` | `/api/train` |
| 推論 | ML-Provide | `/infer` | `/api/infer` |

- 殻が持つのは, 起動, 起動ごとのトークンと Origin と Host の確かめ, 各アプリのバックエンドと画面を載せること, 段階の並び, 共通の部品, 問題の選び方だけ. 各段階の画面と API, 段階のライブラリを使う仕組みは各アプリに置く (段階ごとの中身を 1 か所で直せるようにするため)
- 各アプリは単独でも今まで通り動く. 殻は各アプリが公開する形 (2 の節) だけを使い, 各アプリの中の作りに頼らない (単独の起動と殻の下の起動で同じ API と画面を使うため)
- 段階をまたぐ通しの確かめ (5 つの段階を 1 つのアプリで通す結合テスト) はこのリポジトリが持つ. 各アプリのテストは単独の起動を確かめる

## 2. 使うアプリと約束

5 つのアプリを submodule で持つ (各アプリの版を殻の側で決めて, 組み合わせを再現できるようにするため). 各アプリに求める約束は次の 2 つ.

### バックエンド: `create_api`

各アプリのパッケージ (`ml_pathfinder`, `ml_fathom`, `ml_createarchitecture`, `ml_dashboard`, `ml_provide`) の `app` モジュールが, 次の形の関数を公開する.

```python
def create_api(
    data_dir: Optional[Path] = None, *,
    problems_dir: Optional[Path] = None, ...  # アプリ固有の引数
) -> FastAPI: ...
```

| 引数 | 意味 |
| --- | --- |
| `data_dir` | アプリの置き場. None の場合は各アプリの既定 (環境変数かホームの下) |
| `problems_dir` | 問題の設定の置き場 (`<識別子>/problem.yaml` が並ぶディレクトリ). None の場合は各アプリの今の既定. 決めた値 (既定も含む) は `app.state.problems_dir` に置き, 問題を読む所は全てここから取る (殻が ML-Pathfinder の決めた場所を読んで他に渡せるようにするため) |
| アプリ固有の引数 | 起動時に登録簿に入れる自作の部品. ML-CreateArchitecture は `modules`, ML-Provide は `procedures` と `units` |

返す FastAPI のアプリは次を満たす.

| 決まり | 理由 |
| --- | --- |
| router は頭なし (`APIRouter()`) で作る. 経路は mount の頭を除いた形 (例 `/problems`) | Starlette は mount の頭を除いた経路で照合するので, 頭を殻が決められる |
| トークン, Origin, Host の確かめ, `/api/auth`, 画面の配信を付けない | 殻の下で確かめが重ならないように, 殻が 1 つだけ持つ |
| `docs_url` と `openapi_url` を None にする | API の一覧を外に見せない |
| `app.state` (置き場など) と例外ハンドラは今のまま持つ | mount した sub-app の中では `request.app` が sub-app を指すので, 今の取り方のまま動く |
| `GET /progress?problem=<識別子>` で段階の進みを返す (9 の節の R13) | 殻が段階の物の形を読まずに, 段階の並びに進みを出せるようにするため |
| lifespan と startup, shutdown の処理を使わず, 要る準備は `create_api` の中で済ませる | mount した sub-app の lifespan は Starlette が動かさないため |
| モジュールの読み込みで app を作らず, 呼ぶたびに新しいアプリを返す | テストと殻で別の置き場を渡せるようにする |
| 起動を止める場合 (読めない自作の部品など) は `ValueError` (かその子) を, 利用者に見せる日本語の理由を付けて出す. 同じプロセスの他のアプリの状態 (登録簿の部品など) は消さない | 殻の起動が理由の 1 行を出して終われるように, 型を 1 つにそろえる |

単独の `create_app` は, 確かめと `/api/auth` と画面の配信を付けた外側のアプリに, `create_api(...)` を `/api` の下で加える (今の経路 `/api/...` と振る舞いを保つため).

`GET /progress?problem=<識別子>` は, 次の形の JSON を返す. 問題が置き場に無いときは 404 (殻は印を出さない).

| 項目 | 型 | 意味 |
| --- | --- | --- |
| `state` | `"blocked" \| "running" \| "stale" \| "done" \| "none"` | 段階の状態 (9 の節の R13) |
| `summary` | `string` | 状態の短い文 (例「データセットを書き出した後に問題の答えが変わりました」). 殻は段階の並びの説明に出す |
| `back` | `StageKey \| null` | 戻る段階の鍵. `blocked` では足りない物の段階, `stale` では変わった物の段階. 他の状態では null |

### 画面: 根の部品

各アプリの画面のパッケージが, 段階の画面の根の部品を公開する. 殻は 1 つの画面 (pnpm workspace) に各アプリの部品を取り込む. 取り込みは, 殻の submodule の中の各アプリの画面のパッケージを workspace に加え, そのパッケージの公開する根の部品と CSS を import する形にする (各アプリのビルド済みの画面に頼らず, 1 つのビルドにまとめるため).

| props | 型 | 意味 |
| --- | --- | --- |
| `basename` | `string` | 画面の経路の頭 (例 `/problem`). 部品の中の経路と移動先はこの下に置く. 単独では `""` |
| `apiBase` | `string` | API の頭 (例 `/api/problem`). API の呼び出しは全てこの下に送る. 単独では `/api` |
| `project` | `string \| null` | 殻で選んだ問題の識別子 (5 の節). null の場合は選んでいない |
| `onProjectChange` | `(project: string \| null) => void` | 部品の中で問題を替えたとき (問題の設定の段階で問題を新しく作った, 開いた, 消したときなど) に呼ぶ. 殻は受け取った値が一覧にあるか null なら選んだ問題にし, 一覧に無い値は採らない (3 の節の「選んだ問題は殻が状態として持ち」の項) |
| `onProjectsChange` | `() => void` | 問題の一覧が変わったとき (作った, 名前を変えた, 消した) に呼ぶ. 殻は一覧を読み直す |
| `onStageChange` | `((stage: StageKey) => void) \| undefined` | 次の段階か戻る段階へのボタン (9 の節の R14, R16) で呼ぶ. 殻は段階の並びを押したときと同じに移る. 単独では渡さない (部品はボタンを出さずに文だけを出す) |
| `onProgressChange` | `(() => void) \| undefined` | 段階の物を作る, 保存する, 直す, 消すときと, ジョブの状態が変わるときに呼ぶ. 殻は段階の進みを読み直す (9 の節の R13). 単独では渡さない |
| `embedded` | `boolean` | true の場合はアプリの名前と明暗の切り替えを出さない (殻の上の帯が持つため). 段階の中の移動 (左の欄の項目, 節の並びなど) は今のまま部品の中に出す (狭い画面でも, 段階の中を移る手段を部品が出す). 単独では false |

- 部品は自分の TanStack Query の client を持ち, 画面の中に経路を持つ場合は自分の react-router のルーター (`BrowserRouter` か `createBrowserRouter` に `basename` を渡したもの) も持つ (各アプリの中の画面の作りを殻に出さないため). 殻は react-router を使わない (ルーターが入れ子になると react-router が例外を出すため)
- 部品の中の移動は `basename` の下に留め, 段階をまたぐ移動は自分でせず `onStageChange` で殻に頼む (段階の切り替えは殻だけが行い, 履歴と根の部品の作り直しを 1 か所で扱うため)
- 選んだ問題は props で受け取り, 部品の中の経路や検索パラメータを殻の選びの元にしない (部品の中の移動で選びが落ちないようにするため). 単独では部品が今まで通り自分で選ぶ
- 画面の中で根から始まる絶対パス (`/favicon.svg`, `<a href="/">` など) を使わない. 画像は import してビルドに含め, 段階の頭へ戻る移動は `basename` の下の `Link` にする (殻の下では根が殻の画面を指すため)
- 明暗は殻と同じく `html` 要素のクラス `dark` と `localStorage` の `theme` で持ち, `embedded` のときは読むだけにする (殻の切り替えが全ての段階に効くようにするため)
- 段階に固有の CSS (各アプリの `index.css` のうち, Tailwind の読み込みと色のトークン以外) は, 根の部品と別の CSS として公開する
- トークンは httponly の Cookie で送り, 画面の JS は扱わない (殻と単独で同じ)
- 根の部品は自分の範囲の要素に `data-stage-root` を付ける (箱を作らない `display: contents` でよい). `window` や `document` で聞くキーの操作は, キーの target がこの範囲の中か `body` のときだけ扱う (R9). メニューや対話の枠を `createPortal` で出すときは, 出す先もこの範囲の中にする (範囲の外に出すと, その中のキーを扱えなくなるため. 対話の枠は R12 の `Dialog` で, portal に出さない)
- 保存していない書きかけのうち, 打ち直すのに手間のかかる欄 (フォームの組, モデルの定義, 長い文, 手順の並び) は下書きに残し, 部品が外されるときと `project` が替わるときに待たずに書く (数 1 つや選ぶだけの欄は残さなくてよい. R10). 殻は段階の移動を止めず, 確かめの窓も出さない (部品が殻に移動を止めさせる口を持たず, 段階を自由に行き来できるようにするため)

## 3. 画面

殻の画面は 1 つのページで, 上に共通の帯, その下に選んだ段階の根の部品を置く.

| 部分 | 内容 |
| --- | --- |
| 上の帯 | アプリの名前, 問題の欄, 段階の並び (問題の設定 → データの分析 → モデルの作成・選定 → 学習・評価 → 推論), 明暗の切り替え |
| 段階の画面 | 経路の頭 (`/problem` など) に合う段階の根の部品. `basename`, `apiBase`, 選んだ `project`, `onProjectChange`, `onProjectsChange`, `embedded` (true) を渡す |

- 段階は location の経路の最初の区切り (`/problem` など) で選ぶ. `/` と知らない頭は `/problem` に移す (最初の段階から始めるため)
- 段階の並びを押すと, 殻が `history.pushState` で経路を段階の頭に替え, 段階ごとに別の `key` を付けて根の部品を作り直す (部品のルーターが新しい経路を読み直すようにするため). 戻ると進むで段階をまたいだときは, 殻が `popstate` で知って同じように作り直す
- 段階の中の移動は経路の頭を変えないので, 殻は知らなくてよい (段階を選ぶのに頭しか使わないため)
- 段階の根の部品は段階ごとに分けたチャンクにあり, その段階を初めて開くときに読む (8 の節). 読む間は上の帯を出したまま, 段階の場所に読み込み中と出す (`role="status"`. 帯の操作を待たせず, 何を待っているかを見せるため)
- 段階の画面を読み込めないとき (ネットワークの誤り, 殻の画面を作り直した後に古いファイルの名前を読んだときなど) と, 段階の部品が描く途中で例外を出したときは, 上の帯を出したまま, 段階の場所に出せないことと理由と再読み込みのボタンを出す (`role="alert"`. 1 つの段階の誤りで殻の全体を消さないため). 別の段階に移るときと今の段階を押し直したときに出し直す (段階の中の戻ると進むでは出し直さない). 読めなかった段階は React が失敗を覚えて同じ誤りを返すので, ページの再読み込みで読み直す (作り直した後の新しいファイルの名前も再読み込みで読めるため)
- 段階の並びはいつでも押せ, 段階を移っても選んだ問題を引き継ぐ (前の段階に戻って直せるようにするため)
- 今の段階を押し直すと, 履歴を増やさずに段階の頭から部品を作り直す (段階の中で迷ったときに最初へ戻れるようにするため). 選んだ問題があれば, 作り直した部品がそれを開く
- 選んだ問題は殻が状態として持ち, 根の部品に props で渡す. 再読み込みで保つため, `localStorage` の `studio-project` にも残す (読めない環境では選んでいない形で始める). 上の帯の欄で選んだときと, 部品が `onProjectChange` を呼んだときに替える. 部品が知らせた値が殻の一覧に無いとき (一覧を読み直しても無いとき) は, 殻は採らずに今の値を保つ (殻の一覧に無い識別子を全ての段階に配らないため). 殻の `project` は替わらないので部品には知らせが届かず, 部品はその問題を開いたままのことがある (部品が新しく作った問題は一覧の読み直しの前に知らせが届きうるので, 読み直した後で確かめる). 一覧を読み直せなかったときも採らず, 読み直しの間に別の選び (欄で選んだ, 部品が別の値を知らせた) が入ったときは前の知らせを採らない (後の選びを前の知らせで上書きしないため)
- 明暗は殻が持ち, `html` 要素のクラス `dark` と `localStorage` の `theme` に置く (5 つのアプリと同じ場所にして, 段階の部品がそのまま読めるようにするため)
- 殻の画面のビルドは 1 つで, Tailwind と色のトークンを 1 度だけ読み込み, 5 つのアプリの画面のソースを Tailwind の探す先に加え, 各アプリが公開する段階に固有の CSS を取り込む (同じ規則を何度も読み込まないため). `favicon.svg` は殻が配る
- 段階に固有の CSS は, 段階の部品を分けて読んでも殻の入口 (`main.tsx`) で全ての段階の分を読む (小さく, 規則が段階の要素 (`.react-flow` など) に限られていて段階をまたいで混ざっても困らず, 段階を開いたときに見た目が遅れて替わらないため). 根の部品が自分で import する CSS (ML-CreateArchitecture の React Flow の CSS) は段階のチャンクと一緒に読まれ, 部品を出す前に読み終わる

## 4. API

殻は 1 つの FastAPI のアプリに, 各アプリの `create_api` を 1 の節の表の経路の頭で mount する.

| 経路 | 内容 |
| --- | --- |
| `GET /api/auth?token=` | トークンを確かめて Cookie に置き, `/` に 303 で移す. 合わなければ 401 (5 つのアプリと同じ) |
| `/api/problem/...` など | 各アプリの API (経路の頭を除いた形は各アプリの単独の `/api/...` と同じ) |
| `/assets/...`, その他 | 殻の画面のファイル. `/api` の下以外の他の経路は `index.html` を返す (画面の中の経路のため). `/api` の下で合わない経路は 404 (API の呼び間違いを画面の HTML で隠さないため) |

- 問題の欄の一覧は, 問題の識別子と名前を問題の設定の段階の API (`GET /api/problem/problems`) から読み, 殻は `problem.yaml` の形を読まない (形を ML-Pathfinder だけが知るようにするため)
- 段階の並びの進みは, 選んだ問題で各段階の API の `GET /api/<段階の鍵>/progress?problem=<識別子>` を読み, 返った状態をそのまま出す (殻は段階の物の形を読まず, 段階の間で古さを判定しないため. 9 の節の R13)
- 殻のアプリも `docs_url` と `openapi_url` を None にする

## 5. 用語

| 用語 | 意味 |
| --- | --- |
| 殻 | このリポジトリのアプリ. 5 つの段階のアプリを載せる |
| 段階 | 問題の設定, データの分析, モデルの作成・選定, 学習・評価, 推論の 5 つ. それぞれを 1 つのアプリが受け持つ |
| 段階の鍵 | 経路の頭に使う語. `problem`, `data`, `model`, `train`, `infer` |
| 問題 | 殻で選ぶ 1 つの問題の設定 (ML-Pathfinder の問題の設定の置き場の `<識別子>/problem.yaml` 1 つ). 全ての段階が同じ識別子を受け取る. 各段階が自分の扱う対象 (学習・評価の段階の学習のプロジェクト, 推論の段階の一式など) をこの識別子にどう対応させるかは各アプリが決める |
| `create_api` | 各アプリが公開する, 確かめと画面の配信を持たない API のアプリを作る関数 |
| 根の部品 | 各アプリが公開する, 段階の画面の一番外の React の部品 |
| 共通の部品 | 5 つの段階の画面が同じ形で使う部品 (9 の節の R12). 殻の `parts/common.tsx` が正で, 各アプリが写す |

### 段階をまたぐ言葉

5 つの段階の画面 (見出し, ボタン, 欄の名前, 説明, 確かめの窓, 誤りの文) は, 段階をまたいで出る物と操作を次の語で呼ぶ (1 つのアプリとして使うと, 同じ語が段階ごとに別の物を指したり, 同じ段階が別の名前で出たりすることが利用者の迷いになるため). 単独の起動の画面も同じ語を使う (単独と殻の下で同じ画面を使うため). 各アプリはこの表に合わせる (9 の節の R11).

| 語 | 指すもの | 使わない言い方 |
| --- | --- | --- |
| 問題 | 問題の設定の段階で作る 1 つの問題の設定 (`problem.yaml` 1 つ). 殻の上の帯で選び, 全ての段階が開く | プロジェクト, 課題 (課題の型の語とぶつかるため), 1 つを指す「問題の設定」 |
| 課題 | 問題の設定の段階の中で, 利用者の現実の困りごと (誰の, 何の困りごとか. 問いの 1 の節の名前). 問題 (`problem.yaml`) を指しては使わない | 問題を指す「課題」 |
| 問題の設定 | 1 つ目の段階の名前 (問いに答えて問題を決める) | アプリの名前 |
| データの分析 | 2 つ目の段階の名前 (表を分析し, データセットを書き出す) | データ (段階を指すとき), アプリの名前 |
| モデルの作成・選定 | 3 つ目の段階の名前 (モデルの定義を組んで選ぶ) | モデルの作成, アプリの名前 |
| 学習・評価 | 4 つ目の段階の名前 (学習を起動し, 実験を見比べる) | 学習の段階, ダッシュボード, アプリの名前 |
| 推論 | 5 つ目の段階の名前 (一式を登録して推論する) | アプリの名前 |
| 学習のプロジェクト | ML-Found の骨組み 1 つ (config, `train.py`, README, `problem.yaml` の写しを持つディレクトリ). 問題の設定の段階が書き出し, 書き出した場所を問題に記録する. 学習・評価の段階はこれを登録して学習する. 学習・評価の段階の画面の中だけは「プロジェクト」と縮めてよく, 他の段階と殻では必ず「学習のプロジェクト」と書く (殻の下では上の帯の「問題」と同じ画面に並び, 縮めた語がどちらを指すか分からなくなるため) | Projects などの英語の見出し, 問題を指す「プロジェクト」 |
| データセット | データの分析の段階が書き出す, `dataset.yaml` と分けたデータを持つディレクトリ. モデルの作成・選定の段階と推論の段階が読む | — |
| モデルの定義 | モデルの作成・選定の段階が保存する `model.yaml`. 学習のプロジェクトの中に置く | — |
| 実験 | 学習のプロジェクトで学習を 1 回動かした記録 (ML-Found の実験のディレクトリ 1 つ) | Runs, Experiments などの英語の見出し |
| ジョブ | 学習・評価の段階が画面から起動した学習 1 つ. 状態は学習・評価の段階の状態の印の語 (実行中, 後の処理中, 完了, 中断, 失敗, 未完了) で呼ぶ | Jobs などの英語の見出し |
| 一式 | 学習のスクリプトが実験の中に作る, 推論に要るものの組 (`inference/`). 推論の段階が登録して使う. 初めて出る所では「推論の一式」と呼ぶ | — |

- 他の段階は, アプリの名前 (ML-Fathom など) やライブラリの名前でなく, 段階の名前で呼ぶ (殻の下ではアプリの名前が画面に出ず, 段階の並びのどれか分からないため). 単独の起動でアプリが自分の名前を帯に出すのはよい
- 段階の名前は, 殻の段階の並びと各段階の画面の見出しで同じにする

よく混ざる操作の語は次のように使い分ける.

| 語 | 指すもの | 使わない言い方 |
| --- | --- | --- |
| やめる | 対話の枠や始める前の操作を, 何も変えずに閉じる | キャンセル |
| 止める | 動いている処理 (学習のジョブなど) を途中で終わらせる | キャンセル |
| 足す | 一覧や並びに 1 つ増やす (手順, 列, 入力, タグなど) | 追加, 加える |
| 登録する | 段階の置き場の外に既にあるもの (学習のプロジェクト, 一式) を段階の一覧に載せる. ファイルは作らない | 追加 (登録の意味で) |
| 保存 | 今の中身を, 後で開き直すために残す (段階の置き場か, 開いているファイルに書く). 学習のプロジェクトにモデルの定義を書くのも, モデルの作成・選定の段階で後で開き直すので保存と呼ぶ | 書き出す (同じ意味で) |
| 書き出す | 他の段階か外で使う形のファイルを作る (学習のプロジェクト, データセット) | 保存 (同じ意味で) |
| 書き戻す | 後ろの段階で決めた値を, 前の段階が作ったもの (問題, 一式の `inference.yaml` など) に書く | 保存 (同じ意味で) |
| 上書き | 保存か書き出しの先に既にあるファイルの全体を, 新しい中身で替える. 確かめの窓で聞く | 置き換え (ファイルについて) |
| 書き換える | 既にあるファイルの中の一部 (config の項目, 問題の 1 つの答えなど) を直す. 他の所は残す | 上書き (一部を直すとき) |
| 置き換える | 画面の上の書きかけの中身 (手順の並び, モデルの定義) を, 別の中身 (雛形, 作った手順) で替える. ファイルはまだ変えない | 上書き (画面の上の中身について) |
| 誤り | 入力, 設定, ファイルの中身の正しくない所と, 要求が通らなかった理由 (検証の誤り, 見つからない, 読めない) | エラー |
| 失敗 | 動いた処理 (学習のジョブ, 形の推定など) が正しく終わらなかった終わりの状態. 状態の印の語. 誤りか失敗かに迷うときは, 処理が終わらなかった状態を指すなら失敗, 入力の正しくない所を指すなら誤りと呼ぶ (「形の推定で失敗したもの」は推定が終わらなかったノードなので失敗) | エラー, エラーで止まった |
| 消す | 一覧の項目やファイルを無くす. 登録を一覧から除くだけでファイルを残すときは「登録を外す」 | 削除 |
| 確かめる | 値や状態が正しいかを見る (確かめの窓, データの確かめなど) | 確認 |

- 決めるのは画面の語だけで, コードの識別子, API の経路, ファイルの形の名前 (`project`, `onProjectChange`, `onProjectsChange`, `localStorage` の `studio-project`, `GET /api/problem/problems` など) は替えない (替えると R3 の props と各アプリの API の約束が壊れるため). 画面の語と内部の名前は別のもので, 殻の `project` は画面の「問題」を指す
- ライブラリの出す名前 (`ValueError` など) と, ファイルや config の項目の名前は, 画面でもそのまま出してよい (利用者がファイルの中で探せるようにするため)

## 6. 置き場

殻はサーバーの側に自分の置き場を持たない (選んだ問題と明暗は画面の `localStorage` に持つ).

- 各アプリの置き場 (`data_dir`) は渡さず, 各アプリの既定 (環境変数かホームの下) のままにする (単独で作ったものを殻でも, 殻で作ったものを単独でも開けるようにするため). ML-Pathfinder は `ML_PATHFINDER_HOME` か `~/.ml-pathfinder/`, ML-Fathom は `ML_FATHOM_HOME` か `~/.ml-fathom/`, ML-CreateArchitecture は `ML_CREATEARCHITECTURE_HOME` か `~/.ml-createarchitecture/`, ML-Dashboard は `ML_DASHBOARD_HOME` か `~/.ml-dashboard/`, ML-Provide は `ML_PROVIDE_HOME` か `~/.ml-provide/`. ML-CreateArchitecture の自作の部品 (`modules`) と ML-Provide の自作の部品と手順 (`units`, `procedures`) も渡さず, その既定 (起動の設定 `ML_CREATEARCHITECTURE_MODULES`, `ML_PROVIDE_UNITS`, `ML_PROVIDE_PROCEDURES`) のままにする (単独と同じ設定で同じ部品を使えるようにするため). 殻は既定では ML-CreateArchitecture の extra のうち `project` だけを入れるので, 外部のライブラリの部品のうち, 他の段階のために殻の環境に入るもの (推論の段階が使う torchvision) の部品だけが使え, 他 (huggingface, timm など) は部品の一覧で使えないと出る (殻の 1 つの環境と lock を軽く保つため). 他の部品は, 利用者が選んだ extra を殻の環境に足すと使える (`make setup EXTRAS="timm einops"` か `make extras EXTRAS=...`. 足し方は 8 の節. Linux では torchaudio の部品は足しても使えない)
- 問題の設定の置き場は, 殻が ML-Pathfinder の `create_api()` を先に呼び, その `app.state.problems_dir` を他の 4 つのアプリの `create_api` に `problems_dir` として渡す (場所を決めるのを ML-Pathfinder だけにし, 殻が中の作りに頼らず, アプリごとに場所が食い違わないようにするため)

## 7. 安全

既定では `127.0.0.1` だけで待ち受ける (他のホストを指定すると警告を出す). トークンを持つ人は手元のファイルを読み書きでき, 学習・評価の段階では任意のディレクトリの学習のプロジェクトを登録して, 選んだ Python で学習を起動し, 環境に依存を入れられる (手元でプロセスを起動できる). 推論の段階の既製のモデルなどは重みを出どころの URL から取りに行く (殻から外へ通信する) ので, トークンは他の人に渡さず, 他のホストで待ち受けるときは信頼できる網の中に限る.

- 起動ごとのトークン (環境変数 `ML_STUDIO_TOKEN`, 無ければランダムに作る) を, Cookie (`ml_studio_token_<印>`. 印はトークンから作り, 同じ端末の別の起動と重ならないようにする) かヘッダー `x-studio-token` で受け取り, `/api` の下の全ての要求で確かめる. 外すのは `GET /api/auth` だけで, 他のメソッドの `/api/auth` も確かめる (トークンを受け取る入口だけを開けるため). 合わなければ 401. 比べるときは時間で推測されない比べ方を使う
- 書き込みの要求 (GET, HEAD, OPTIONS 以外) は, Origin が接続先と違えば断る (他のサイトからの書き込みを防ぐため)
- 受け付けるホスト名を決め (既定は `127.0.0.1` と `localhost`), 他のホスト名での接続を断る (DNS の付け替えを防ぐため). `--host` に名前かアドレスを渡したときはそれも受け付け (出した URL をそのまま開けるようにするため), さらに足すときは `--allowed-host` (何度も渡せる) で足す. IPv6 のアドレスでの接続は受け付けない (受け付ける形を決めていないため)
- この 3 つの確かめは殻のアプリだけが持ち, mount した各アプリの API は持たない (確かめが重なると, トークンの名前や Cookie が段階ごとに分かれて 1 つの画面から呼べないため)

## 8. 起動と載せ方

- 起動は 1 つのコマンド `ml-studio` (`--host`, `--port`, `--allowed-host`). 各アプリの設定は各アプリの環境変数のまま (6 の節). 起動するとトークン付きの `/api/auth` の URL を出す. 段階のアプリが起動を止めた場合 (読めない自作の部品など) は, 理由を出して終わる
- 1 つのプロセス (worker 1 つ) で動かす. 学習・評価の段階のジョブの管理と, 起動時に部品を入れる登録簿がプロセスの中の状態のため
- 学習・評価の段階のアプリは 1 つのプロセスで 1 度だけ作り, 同じ置き場を 2 つのアプリに渡さない (ジョブのプロセスとロックをアプリごとに持つため). 学習のジョブは登録した学習のプロジェクトの Python の子プロセスとして動き, 学習のまとまりと環境の準備は殻のプロセスの中のスレッドで進む
- 自作の部品の登録簿 (ML-ModelControl の登録簿) はプロセスに 1 つで, 部品を入れるアプリ (モデルの作成・選定の段階, 推論の段階) の間で共有になる. 同じモジュールは 1 度だけ入り, 2 つのアプリの起動の設定に同じモジュールを書いてよい (殻のテストで, 両方に書いて起動し, モデルの作成・選定の段階で確かめて保存した定義から推論の段階で一式を作って推論できることを確かめる). 同じ部品の名前を別々のモジュールで宣言すると, 後から `create_api` を呼んだアプリ (段階の並びの後ろ) が起動を止める. モデルの作成・選定の段階の部品の一覧は登録簿の全体を出すので, 他のアプリが入れた部品も出る. 推論の段階も登録簿の全体から組み立てるので, モデルの作成・選定の段階の起動の設定にだけ書いた部品も殻の中では使え, その一式を推論の段階を単独で開くと部品が無い誤りになる (単独でも使う一式の部品は, 推論の段階の起動の設定にも書く)
- 殻は 5 つのアプリの `create_api` を段階の並びの順に 1 度ずつ呼んで mount する. ML-Pathfinder を先に呼び, その問題の設定の置き場を他に渡す (6 の節). 各アプリの例外ハンドラ, 子プロセス, スレッドは mount した sub-app の中でそのまま動く
- 各アプリの画面は殻の画面のビルドに取り込み, 各アプリのビルド済みの画面 (`static/`) は使わない (共通の部品と 1 つのビルドにまとめるため)

### 載せた段階と依存

| 段階 | アプリ (submodule) | アプリが submodule で持つライブラリ |
| --- | --- | --- |
| 問題の設定 | `ML-Pathfinder/` | ML-Quest |
| データの分析 | `ML-Fathom/` | ML-EDA, ML-Quest |
| モデルの作成・選定 | `ML-CreateArchitecture/` | ML-ModelControl (ML-EDA と ML-Quest は git の依存. extra `project`) |
| 学習・評価 | `ML-Dashboard/` | ML-Found, ML-Quest (extra `problem`) |
| 推論 | `ML-Provide/` | ML-Inference, ML-Quest (ML-EDA と ML-ModelControl は git の依存. ML-Inference も ML-EDA と ML-ModelControl を `tool.uv.sources` の git で求める) |

- submodule の中の submodule も取る (`git submodule update --init --recursive`. CI の checkout も `submodules: recursive`). 各アプリがライブラリを submodule で持ち, 殻はそれを使うため
- バックエンドは 1 つの Python の環境 (uv) に, 各アプリのパッケージとライブラリを submodule から editable で入れる (`backend/pyproject.toml` の `tool.uv.sources`). アプリが git の依存で求めるライブラリ (ML-CreateArchitecture の ML-EDA と ML-Quest, ML-Provide の ML-EDA と ML-ModelControl) と, ライブラリが `tool.uv.sources` の git で求めるライブラリ (ML-Inference の ML-EDA と ML-ModelControl) も, 下の上書きで殻の 1 つの求め方に置き換える (上書きしないと, submodule の求めと URL がぶつかって解けないため). PyTorch と torchvision は ML-CreateArchitecture, ML-Dashboard, ML-Provide と同じく Linux では CUDA の無い版の index から取る (index はアプリの pyproject.toml のものが効かず, 殻の pyproject.toml に書く要があるため. CI の時間と大きさを抑えるため)
- 同じライブラリを 2 つ以上のアプリが使う場合は, 殻の `tool.uv.override-dependencies` で 1 つの求め方に上書きし, `tool.uv.sources` でアプリの submodule のうち 1 つ (今は ML-Fathom の ML-EDA と ML-Quest, ML-CreateArchitecture の ML-ModelControl) を指す (1 つの環境には 1 つの版しか入らず, アプリごとの submodule の版や git の版の求めがぶつかるため). 各アプリの submodule の版は下の「共通のライブラリの版」にそろえる (R8). 上書きは extra ごと置き換えるので, 各アプリが使う extra を全て書く. そろえた版で各段階の API が動くことは, CI で殻の環境のまま各アプリのテストを流して確かめる (殻のテストと通しの確かめは各段階の API の一部しか通らないため)
- 外部のライブラリの部品の extra (ML-CreateArchitecture の extra のうち `project` 以外. 中身は ML-ModelControl の同じ名前の extra) は殻の `pyproject.toml` と `uv.lock` に書かず, 利用者が殻の環境に足す (`make extras EXTRAS="..."` は前に足した extra を残して足し, `make setup EXTRAS="..."` は既定に戻してから選んだ extra だけを入れる) (lock に書くと, 使わない利用者と CI の lock と解決が大きくなるため). 名前は入っている ML-CreateArchitecture と ML-ModelControl の両方の extra と照らし (`scripts/check_extras.py`. 片方だけにある名前は, uv が警告だけを出して何も入れずに通るため. 選べる名前は `make extras-list`), `uv pip install` で ML-ModelControl を選んだ extra 付きで入れ直す. `project` は殻が既定で入れる extra なので, 書いても誤りにせず, 入れ直す対象と選べる名前の一覧からは外す (ML-CreateArchitecture が理由に出す単独の起動での入れ方 `make setup EXTRAS="project timm"` を殻でそのまま使えるようにするため). 外した残りが空なら何も入れずに終わる. `EXTRAS` は make の引数だけから読み, 同じ名前の環境変数は読まない. 殻の環境 (`backend/.venv`) が無ければ作らずに止まる. そのとき `uv.lock` の版を制約にして, 入っているライブラリ (Linux の CUDA の無い PyTorch と torchvision を含む) を替えない (制約は 1 度ファイルに書き, 書けた場合だけ入れる). lock に無いライブラリ (torchaudio など) は殻の index の設定を読まないので PyPI から入る. そのため Linux では torchaudio (と `all`) を足しても, 上流の torchaudio が殻の torch (2.15) に合う版を出していない (2.11 まで) ので読み込めず, torchaudio の部品は使えないと出る (macOS では使える). 殻の `override-dependencies` は `ml-modelcontrol` を extra 無しに置き換え, `uv pip` もその設定を読むので, 足すときは殻の設定を読まない (`--no-config`). `--no-config` は利用者の uv の設定ファイル (`uv.toml` の `index-url` や `native-tls` など) も読まないので, それらが要る場合は環境変数 (`UV_INDEX_URL`, `UV_NATIVE_TLS` など) で渡す (環境変数は効くため). 足したライブラリは `uv run` (足りない物だけを入れる) では残り, `uv sync` (lock に無い物を消す) で消えて既定に戻る. lock を上げた後は足したライブラリが前の版のまま残るので, `make setup EXTRAS="..."` で入れ直す. CI は既定の環境のまま確かめ, 殻のテストは部品の一覧の使える部品が環境で読み込めるライブラリと合うことを確かめる (extra を足した環境でも同じテストで確かめられる)
- 画面は 1 つの pnpm workspace (`frontend/pnpm-workspace.yaml`) に各アプリの画面のパッケージを加え, 共通の依存 (react, react-router, TanStack Query など) を 1 つの版に解く. react と react-dom は vite の `dedupe` でも 1 つにする (2 つ読むとフックが動かないため). 開発用のサーバーが submodule の画面のソースを配れるよう, vite の `server.fs.allow` に各アプリの画面のディレクトリを加える
- 画面のビルドは殻の入口 (上の帯と段階の並び) と段階ごとのチャンクに分け, 段階の根の部品は `React.lazy` と動的な `import()` で, その段階を開いたときに読む (図の部品やキャンバスの部品で段階の部品の全体が 2.7 MB 近くあり, 1 つにまとめると段階を足すたびに最初の読み込みが重くなり, 段階を足すと大きさの閾値も超えるため). 段階の間で共通の依存 (react-router, TanStack Query など) は Vite が別のチャンクに分けて使い回す. 大きさの警告の閾値は 2500 kB のままにし, 上げない. 段階を足すときも同じ形で分ける

### 共通のライブラリの版

2 つ以上のアプリが使う (submodule で持つか, git の依存で持つか, 持つライブラリを通して求める) ライブラリの版 (コミット) を殻が決め, そのライブラリを submodule か git の依存 (`backend/pyproject.toml` の `tool.uv.sources` の `git`. 版は `backend/uv.lock` が決める) で直に持つアプリはその版に合わせる (R8). git の依存は `tool.uv.sources` で書き, `dependencies` に `@ git+...` の形で書かない (確かめが sources から git の依存を探すため). 殻の木の中の同じライブラリは 1 つの版にする. この表が版を書く唯一の場所で, 殻の確かめもこの表を読む (版を 2 か所に書くと食い違うため).

| ライブラリ | 版 | 使うアプリ |
| --- | --- | --- |
| ML-Quest | `713a2c0` | ML-Pathfinder (submodule), ML-Fathom (submodule), ML-CreateArchitecture (git の依存), ML-Dashboard (submodule), ML-Provide (submodule) |
| ML-EDA | `14e9b8e` | ML-Fathom (submodule), ML-CreateArchitecture (git の依存), ML-Provide (git の依存. ML-Inference を通しても), ML-Pathfinder (ML-Quest を通して) |

### 段階をまたぐ要求

R13 から R18 は, 利用者が殻で 1 つの問題を課題から推論まで進めるときに, 段階をまたいで要ること. R1 から R12 は段階を 1 つのアプリに載せる形を決め, ここでは載せた段階の間の流れを決める. 殻が持つのは段階の並びと問題の選び方に収まる所 (印を出す, 段階を移す, 選んだ問題を保つ) だけで, 段階ごとの物の有無と新しさ, 前提の確かめ, 案内の文は各アプリが決める (段階の物の形を, その段階のアプリだけが知るようにするため). 殻が各アプリの API を読むときは, 各アプリが公開する形 (2 の節) だけを読む.

各段階の物は次の通り. 各段階は直前の段階の物から作るので, 前が変わると後ろが古くなる. 印は, 段階の物を作るときに直前の物から取って自分の物に残す.

| 段階 | 段階の物 | 直前の物 | 残す印 |
| --- | --- | --- | --- |
| 問題の設定 | 学習のプロジェクト (問題に場所を記録) | 問題の答え | 学習のプロジェクトの中の `problem.yaml` の写し |
| データの分析 | データセット (`project.dataset` の場所) | 問題 | 問題の答えの版 (名前と場所の記録を除いた中身の sha256. 問題の設定の段階が返す) |
| モデルの作成・選定 | モデルの定義 (`project.model_spec` の場所) | データセット | `dataset.yaml` の sha256 |
| 学習・評価 | 実験 | モデルの定義, データセット | モデルの定義と `dataset.yaml` の sha256 (実験の `source.yaml`) |
| 推論 | 一式 | 実験, 問題 | 一式の元の実験と, つないだ問題 (今の問題との食い違いを毎回比べる) |

- 段階の物が 1 つの問題にいくつもあるとき, 学習・評価の段階は完了した実験のうち最も新しいものの印で, 推論の段階は問題につないだ一式のどれかに食い違いがあるかで決める
- 各段階が比べるのは直前の物だけで, 殻は段階の間で古さを伝えない (問題を直すとデータの分析の段階が古いと出し, データセットを書き出し直すとモデルの作成・選定の段階が古いと出す. 古さは作り直すごとに 1 段ずつ後ろへ進む. 何が古いかを決められるのは物の形を知る各アプリだけのため)
- 印を残す前に作った物 (印が無い物) は, 新しさが分からないので古いと出さない (今ある物を, 比べられないだけで古いと見せないため)
- 前の段階の物を消したときは, 後ろの段階の物を消さず, 後ろの段階は前提が足りないと出す. 問題を消したときは, その問題の後ろの段階の物は残り, 殻はどの問題も選んでいない形になる (物を消すのは, その物の段階で利用者が決めるため)

#### R13. 段階の進み

- 中身: 殻で選んだ問題について, 段階ごとの物の有無と新しさを, 上の帯の段階の並びの 1 か所で見せる (どこまで進んだかを, 段階を 1 つずつ開かずに分かるようにするため). 状態は次の 5 つで, 上にあるものほど先に採る. 最初の「まだ無い」の段階を次にする段階として目立たせる

| 状態 (値) | 意味 |
| --- | --- |
| 前提が足りない (`blocked`) | 直前の物が無い. 条件は R16 と同じで, 段階ごとに R16 に書く |
| 動いている (`running`) | 段階の物を作る処理が動いている (学習・評価の段階のジョブが実行中か後の処理中) |
| 古い (`stale`) | 段階の物があり, 残した印が今の直前の物と違う |
| ある (`done`) | 段階の物があり, 印が今の直前の物と同じか, 印が無い (印が無いときは短い文で新しさが分からないと書く) |
| まだ無い (`none`) | 直前の物はあり, 段階の物がまだ無い |

- 殻が持つもの: 問題を選んだとき, 段階を移ったとき, 部品が `onProgressChange` を呼んだときに, 5 つの段階の進み (`GET /api/<段階の鍵>/progress?problem=<識別子>`) を読み直す. 段階の並びの各段階に, 返った状態をそのまま印にし, 状態を含む名前 (例「データの分析 (古い)」) と短い文を付ける. 読めない段階は印を出さない. 問題を選んでいないとき (一覧に無い問題を選んでいるときも) は印を出さず, 問題を選ぶと進みが出ると書く
- 各アプリが持つもの: `GET /progress?problem=<識別子>` (2 の節) で, 自分の段階の状態, 短い文, 戻る段階の鍵 (`blocked` と `stale` のとき) を返す. 物を作る, 保存する, 直す, 消すときと, ジョブの状態が変わるときに `onProgressChange` を呼ぶ
- 確かめ方: 見本の問題を課題から推論まで進めると, 各段階の印が「まだ無い」から「ある」に替わり, 次にする段階が 1 つ後ろに移る. 学習の間は学習・評価の段階が「動いている」と出る. 問題を選んでいないときは印が出ない
- 今の動き: 段階の並びは段階の名前と今の段階の印 (`aria-current`) を出す. 段階ごとの物の有無を返す API は次の通り. 問題の設定の段階の `GET /problems` は答えの進み (`progress`, `ready`, `finished`) を返し, `GET /problems/{id}` は記録した場所 (`project`) を返す. データの分析の段階の `GET /sources/{id}/project` は, 登録したデータの単位で書き出し先の様子 (`state` が `missing` (無い), `dataset` (前に書き出したデータセット), `occupied` (データセットでないディレクトリかファイルかシンボリックリンク. 上書きせずに断る)) を返す. モデルの作成・選定の段階は保存先の有無 (`POST /project/target` の `exists`) を上書きの確かめに使う. 学習・評価の段階の `GET /problems/{id}/project` は記録した学習のプロジェクトと登録の有無を返し, 実験の数 (`run_count`) は `GET /projects` の学習のプロジェクトの単位で返す. 推論の段階は `GET /experiments?project=` (一式を持つ実験) と `GET /bundles` の `problem_id` で問題の一式を引ける

#### R14. 次にすることと段階の移り

- 中身: 各段階の主な操作 (学習のプロジェクトの書き出し, データセットの書き出し, モデルの定義の保存, 学習の完了) を終えた所に, 次にすることの文と, 次の段階へ移るボタンを出す (段階の名前を読んで帯の並びから探さずに進めるようにするため)
- 殻が持つもの: 根の部品に `onStageChange(stage)` を渡し, 呼ばれたら段階の並びを押したときと同じに移る (履歴を増やし, 根の部品を作り直す. 段階を移すのは今まで通り殻だけ)
- 各アプリが持つもの: 主な操作を終えた所に, 次にすることと「<段階の名前>の段階へ」のボタンを出し, `onStageChange` を呼ぶ. 単独の起動 (`onStageChange` が無い) では文だけを出す. 推論の段階は最後なので持たない
- 確かめ方: 殻の下で各段階の主な操作の後のボタンを押すと, 次の段階が殻で選んだ問題のまま開く
- 今の動き: 問題の設定の段階は, 書き出した後に「次にすること」の手順を出し, データの分析とモデルの作成・選定の段階を名前で書く. データの分析の段階は, 書き出した後に書き出した場所とモデルを組むときの数を出す. モデルの作成・選定の段階は, 保存した後に保存した場所を出す. 学習・評価の段階は, 実験の詳細の「この実験を推論の段階で使うには」で, 推論の段階の「実験の一覧から登録」か「学習の結果から作る」を名前で書く

#### R15. 前を直したときに後ろが古いと分かる

- 中身: 前の段階の物 (問題の答え, データセット, モデルの定義) を直した後に, それから作った後ろの段階の物が古いと分かる (古い物のまま学習や推論を進めないようにするため). 古さは上の表の鎖の全て (問題 → 学習のプロジェクト, 問題 → データセット → モデルの定義 → 実験 → 一式) で出す
- 殻が持つもの: R13 の印で, 各アプリが返した「古い」を出す (殻は段階の間で古さを判定しない)
- 各アプリが持つもの: 段階の物を作るときに, 上の表の印を自分の物に残す. 進みと段階の画面で, 残した印と今の直前の物を比べ, 違えば古いと出し, 何が変わったかと作り直す操作を段階の画面に出す. 印が無い物は古いと出さない
- 確かめ方: データセットを書き出した後に問題の目的の列の答えを替えると, データの分析の段階が古いと出る. モデルの定義を保存した後にデータセットを書き出し直すと, モデルの作成・選定の段階が古いと出る. 実験の後にモデルの定義を保存し直すと, 学習・評価の段階が古いと出る. 一式を作った後に問題の結論の決め方を替えて食い違うと, 推論の段階が古いと出る
- 今の動き: 問題の設定の段階は, 問題の中身の sha256 を `GET /problems/{id}/version` で返し (名前と場所の記録を書き換えても替わる), 画面は他での書き換えに気付くのに使う. 学習のプロジェクトには `problem.yaml` の写しを置き, 写しは元の場所 (`origin`) を持つ. データの分析の段階は, 始めた問題が別の問題に替わったか (`created_at`) を確かめる. 学習・評価の段階の実験には, ML-Found がモデルの定義の写しと sha256 (`source.yaml`) を残し, 写しを使えずに学習し直すときに今の定義と比べる. 推論の段階は, 一式と今の問題の食い違い (目的の列, 意思決定, 結論の決め方など. `issues`) を表示のたびに比べる

#### R16. 前提が足りないときの戻り先

- 中身: 直前の物が無い段階を開いたとき (データセットが無いのにモデルの作成・選定の段階を開くなど) に, 段階の頭の画面で, 何が足りないかと戻る段階を 1 つの文で出し, その段階へ移るボタンを出す (足りない物がどの段階の物かを利用者が探さずに戻れるようにするため). 条件は R13 の「前提が足りない」と同じで, 段階ごとに次の表で決める

| 段階 | 前提が足りない条件 | 戻る段階 |
| --- | --- | --- |
| 問題の設定 | 無し (最初の段階) | — |
| データの分析 | 問題にデータが入っていない, か学習のプロジェクトの記録 (`project.dataset`) が無い | 問題の設定 |
| モデルの作成・選定 | 学習のプロジェクトの記録が無い | 問題の設定 |
| モデルの作成・選定 | データセットの記録の場所にデータセットが無い | データの分析 |
| 学習・評価 | 学習のプロジェクトの記録が無いか, 記録の場所に学習のプロジェクトが無い | 問題の設定 |
| 学習・評価 | データセットの場所にデータセットが無い | データの分析 |
| 学習・評価 | モデルの定義が無く, 仮のモデルの目印も無い | モデルの作成・選定 |
| 推論 | 問題の学習のプロジェクトに, 一式を持つ実験が無い | 学習・評価 |

- 殻が持つもの: R14 の `onStageChange` を渡し, R13 の印で「前提が足りない」を出す
- 各アプリが持つもの: 段階の頭の画面で上の表の条件を確かめ, 足りない物, 戻る段階の名前, その段階へのボタンを出す. 進みの `blocked` も同じ条件で返す
- 確かめ方: 殻で学習のプロジェクトだけを書き出した問題を選び, モデルの作成・選定の段階を開くと, データの分析の段階へ戻る文とボタンが出て, 押すとデータの分析の段階が開く
- 今の動き: データの分析の段階は, データが無いときに「データが入っていません (問題の設定の段階の「手元のデータは」で入れてください)」, 学習のプロジェクトの記録が無いときに「…問題の設定の段階で学習のプロジェクトを書き出してください」と出す. モデルの作成・選定の段階は, 「データセットと学習のプロジェクト」の対話の枠の中で, 学習のプロジェクトが無いときに「学習のプロジェクトを書き出していません (問題の設定の段階で書き出してください. …)」と出す. 学習・評価の段階は, 学習のプロジェクトの記録が無いときに「学習のプロジェクトの記録がありません. 問題の設定の段階で学習のプロジェクトを書き出してください」と出し, 実験の一覧の学習の準備の欄で, データセットが無いときに「データの分析の段階でデータセットをこの場所に書き出します」, モデルの定義が無いときに「モデルの作成・選定の段階で定義をこの場所に置きます」と出す. 推論の段階は, 実験の一覧で選んだ問題に一式を持つ実験が無いときに「選んだ問題が記録した学習のプロジェクトに, 一式を持つ実験がありません. 全ての問題の実験を出すか, 「場所で登録」を使います.」, 絞らずに無いときに「一式を持つ実験がありません (…). 問題の設定の段階で学習のプロジェクトを書き出して学習するか, 「場所で登録」を使います.」と出す

#### R17. 選んだ問題を URL に持つ

- 中身: 上の帯で選んだ問題を URL に入れ, 段階をまたいでも, 再読み込みでも, 直接の URL と別のタブでも同じ問題になる (URL を残すか渡すと同じ所を開け, タブごとに別の問題を開けるようにするため)
- 殻が持つもの: 選んだ問題を URL の殻が持つ所に入れ, 段階の中の移動で落ちない形にする (形は 3 の節に書く). 開いたときは URL の問題を先にし, URL に無いときだけ `localStorage` の `studio-project` を使う
- 各アプリが持つもの: 無し (根の部品の `project` を今まで通り受け取る)
- 確かめ方: 問題を選んで段階の中を移った URL を別のタブで開くと, 同じ問題と同じ画面が開く. 2 つのタブで別の問題を選んで再読み込みすると, それぞれの問題のまま
- 今の動き: 選んだ問題は殻の状態と `localStorage` の `studio-project` に持つ. 開いたときは `studio-project` を読むので, 直接の URL では前に選んだ問題で開き, 2 つのタブで別の問題を選ぶと, 後に選んだ方が両方の次の読み込みの選びになる

#### R18. 開いている物と選んだ問題を合わせる

- 中身: 段階の中の URL が開く物 (データ, 学習のプロジェクト, 一式など) が殻で選んだ問題の物でないとき (R17 の前に残した URL を開いたなど) に, 食い違いを出す (他の問題の物を選んだ問題の物と取り違えないため). R17 で URL が問題を持つと多くは起きないが, 問題に属さない物の経路が残る間は要る
- 殻が持つもの: 無し
- 各アプリが持つもの: 開いた物が `project` の問題の物でなければ, 段階の画面に「開いている<物>は選んだ問題の物ではありません」の文と, 選んだ問題の物の一覧へ移るボタンを出す. 殻の選びは替えない (殻の選びの元を殻の欄と URL だけにするため. 部品の中の経路を殻の選びの元にしない 2 の節の決まりのまま)
- 確かめ方: 問題 A の物を開いた URL を, 殻で問題 B を選んだまま開くと, 食い違いの文が出る
- 今の動き: 問題の設定の段階は, 最初に受け取った `project` の問題へ移る. データの分析の段階 (`/sources/{id}`), 学習・評価の段階 (`/projects/{id}`), 推論の段階 (`/bundles/{id}`) は, 再読み込みと直接の URL では URL の物を開き, 殻で選んだ問題が後から替わったときに一覧へ移る (推論の段階は移らない). モデルの作成・選定の段階は画面の中に経路を持たない

### 共通の部品

5 つの段階の画面は, 次の部品を殻の正のファイルの写しから使う. 正は部品の `parts/common.tsx` と, 部品でない関数 (`errorText`, `tabPanelProps`, `describedBy`) の `parts/common-utils.ts` の 2 つで, 各アプリはそのまま `frontend/src/components/` の同じ名前のファイルに写し, 段階に固有の部品 (ML-Dashboard の状態の印, ML-CreateArchitecture の例を選ぶボタンなど) は `components/ui.tsx` に置いて, そこから `common` と `common-utils` を書き出してよい (部品の import の先を `ui` のままにできるため). 部品と関数のファイルを分けるのは, 部品のファイルが部品だけを書き出すようにするため (oxlint の `react/only-export-components` の警告を出さず, 開発のときの部品の差し替えが効くため). 部品の形を変えるときは, 先に殻の正とこの表を直し, その後に各アプリが写し直す.

#### 誤りの出し方

- API の誤り (要求が通らなかった理由) は `ErrorBox` で出す. API を呼ぶ所は, 応答が ok でないときに `errorText(status, statusText, body)` で文を作り, その文を `Error` の文にして投げる. `ErrorBox` がその文を出す. 誤りが 1 つの欄に関わるときは `ErrorBox` に `id` と `live={false}` を渡し, 欄の `aria-describedby` で結ぶ
- 入力の確かめの短い誤り (欄の値が正しくない, 空など. 要求を送る前に画面で分かるもの) は, 欄の下に `FieldError` で出し, 欄に `aria-invalid` と `aria-describedby={describedBy(...)}` (説明と合わせる) を付けて結ぶ (欄ごとの短い文を `ErrorBox` の枠で囲むと, 誤りが並んだときに欄より目立つため. `FieldError` が役割を持たないのは, 欄に focus したときに読まれれば足り, 打つたびに読み上げると邪魔になるため)
- `detail` が文ならそのまま出す. ただし FastAPI の既定の 404 (`detail` が英語の `Not Found`) は「API の経路が見つかりません (404)」と出す (段階の API は見つからない物を日本語の文で返すので, 既定の英語の文は経路の呼び間違いのときだけのため). 見つからない (404) の文は API が「<物> <識別子> が見つかりません」の形で返し, 画面は足さない (何が見つからないかを API が一番よく知るため). <識別子> は物の識別子か, 識別子を持たない物では場所 (「ディレクトリ <場所> が見つかりません」など) にする. 画面の中の知らない経路は下の「見出し」の形で出す
- `detail` が入力の検証の誤りの配列 (422) なら, 1 件ずつ「欄: 理由」の行にして改行でつなぐ. 欄は `loc` の先頭が置き場所の印 (`body`, `query`, `path`, `header`, `cookie`) ならそれだけを除き, 残りを `.` でつなぐ (どの欄を直すかが読めるように. 先頭だけを見るのは `path` という名前の欄を消さないため. 生の JSON は出さない). 行が 1 つもできない (`detail` が空の配列など) ときは「状態の番号 状態の文」を出す
- `detail` が画面の文 `message` を持つ形 (保存の 409 など) なら `message` を出す. 段階は `detail` の残りを別に読んで, 直す場所の一覧などを足して出してよい
- 本文が JSON でないか `detail` を持たなければ「状態の番号 状態の文」を出す
- 複数の誤り (書き出せない理由など) は改行でつなぎ, `ErrorBox` が 1 行ずつ出す
- 確かめの窓 (消す, 上書きなど戻せない操作の前に聞く窓) はブラウザの `window.confirm` を使い, 文は 5 の節の語で書く

#### 対話の枠

- 対話の枠は `Dialog` を使い, 開いている間だけ部品を置く (閉じたら外す). 役割は `dialog` で, 名前は見出しの `title` (e2e も役割と名前で選ぶ)
- Esc, 枠の外 (背景) を押す, 見出しの右の「閉じる」のボタンのどれでも閉じ, `onClose` を呼ぶ. 外を押したと見るのは, 押し始め (pointerdown) も離した所 (click) も背景で, 離した位置が枠の矩形の外のときだけにする (枠の中で文字を選び始めて外で離したときに閉じないため). `busy` の間 (登録の途中など) はどれでも閉じず, 閉じるのボタンを押せなくする (処理の結果を見せるため)
- 閉じたら, 開く前に focus があった要素に focus を戻す. その要素が作り直されて無いときは, 同じ `data-return` の印を持つ要素に戻す
- 開いたときの focus は `initialFocus` の要素に置き, 渡さなければブラウザの決まり (`autoFocus` の要素, 無ければ枠の中の最初の focus できる要素. 多くは「閉じる」のボタン) に任せる. 最初に打つ欄があるときは `initialFocus` か `autoFocus` でその欄に置く
- 枠の中の対話 (ファイルを選ぶなど) の閉じる知らせと Esc の知らせ (cancel) で, 外の枠を閉じない (知らせの target が外の枠のときだけ扱う)
- `Dialog` は部品の木の中に置き, `createPortal` で外に出さない (ブラウザの `dialog` は木の中のまま一番上に出るため). 他の部品を portal で出すときも, 出す先は `data-stage-root` の中にする (R9)

#### 見出し

- 画面ごとに `PageHeader` を 1 つ置き, その `h1` を画面の見出しにする (殻の上の帯は `h1` を持たないので, 殻の下でも 1 つの画面に `h1` が 1 つになる)
- 段階の頭の画面 (`basename` の直下) の `title` は段階の名前 (5 の節) にする. R11 の「自分の段階の見出しも段階の名前にする」はこの `h1` を指す. 下の画面は開いた物の名前 (問題の名前, 実験の識別子など) を `title` にし, `breadcrumb` の頭に段階の名前で段階の頭の画面へのリンクを置く (殻の段階の並びと同じ名前で, 今どの段階のどこにいるかが分かるように)
- 読み込み中の画面にも `PageHeader` を置く (読み込みが終わって見出しが現れるまで, 画面に `h1` が無い間を作らないため). 段階の頭の画面は `title` を段階の名前にし, `breadcrumb` を置かない. 下の画面は `breadcrumb` の頭に段階の名前で段階の頭の画面へのリンクを置き, `title` は経路から物の名前 (識別子) が分かればその名前, 分からなければ段階の名前にする (パンくずと見出しに段階の名前が並んでよい)
- 物を開けないとき (見つからない, 読めないなど) は `title` を「<物>を開けません」(「問題を開けません」など) にし, 読み込み中と同じ `breadcrumb` を置く. 誤りの文は `ErrorBox` に `live={false}` を付けて出す (画面を開いたときの読み込みの誤りのため)
- 画面の中の知らない経路は, 段階の名前の `PageHeader` (`h1`) を置き, `EmptyState` の「ページが見つかりません」(既定の `h2`) と段階の頭の画面へのリンクを出す
- 段階の画面の全体を使う画面 (モデルの作成・選定の段階の編集の画面など) で `PageHeader` を置けないときも, 段階の名前の `h1` を 1 つ置く (狭い画面では見えなくしてよい). アプリの名前を `h1` にしない

#### 色違いの枠

- 色違いの枠は `Card` の `tone` で出し, 段階で自分の枠 (`section` に色の class を付けたものなど) を作らず, `className` で色と枠線を上書きしない (`className` の上書きは Tailwind の class の順や `!` に頼り, 正の枠の形が変わると段階ごとに見た目が崩れるため. 色の形を正に持てば, 5 つの段階で同じ役目の枠が同じ色になる)
- `tone` の形は, 5 つのアプリで使っている色違いの枠の役目から, `default` の他に 3 つだけ持つ. 足りない形は殻の正に足す

| `tone` | 見た目 | 使う所 |
| --- | --- | --- |
| `default` | `border-line` の枠と `bg-surface` | 普通の欄 |
| `accent` | 薄い `border-accent/30` の枠 (見出しの区切り線も同じ色) と `bg-accent-soft` | 画面を止めずに先の段階の準備などを知らせる欄 (問題の設定の段階の, 学習・評価の段階で要る機能の欄など) |
| `warning` | `border-warning/60` の枠と `bg-surface` | 決めてほしいことなど, 注意を促す欄 (データの分析の段階の「決めてほしいこと」の欄) |
| `highlight` | 太い `border-accent` の枠と `bg-surface` | 同じ形の欄の並びの中で 1 つを目立たせる欄 (学習・評価の段階の守りの指標の評価の欄, データの分析の段階の問題の欄など). 色だけで違いを表さず, 文やバッジと併せて使う (色を見分けにくい人と読み上げにも違いが伝わるため) |

#### 確かめ方

- 殻の CI の `docs` のジョブで `scripts/check_parts.py` が, 各アプリの `frontend/src/components/` の写しを `parts/` の正と SHA-256 で比べ, アプリとファイルごとに合う, 違う (差の行の数), 無いを出す. 既定は差を出すだけで 0 で終わり, `--strict` のときだけ差で 1 で終わる. 殻の CI は `--strict` で動かす (5 つのアプリの写しが正と合っているので, 正を直したのに写しを上げ忘れたアプリを殻の submodule に載せないため. 正を直すときは, 各アプリが写しを上げた後に殻の submodule と正を 1 つの PR で上げる). 知らない引数と正のファイルが無いときは 2 で止まる
- ファイルの写しを比べる形にし, 書き出しの名前と props の型を比べる形にしない (名前と型が合っても class や役割や動きが違えば見た目と動きがそろわず, それを比べるには部品の中身を比べるしかないため. 5 つのアプリは同じ Prettier の設定と同じ依存 (clsx, lucide-react, react) を持つので, 1 字も違わない写しを置ける. 写しは 1 つのパッケージに移すときもそのまま使える)
- 正は殻の画面のビルドに入れない (殻は clsx を依存に持たず, 正を使うのは各アプリのため). 殻の CI の `frontend` のジョブで `scripts/lint_parts.sh` が, 正を ML-Pathfinder の画面の `src` の下の一時の置き場に写し, そのアプリの `node_modules` と設定で型の検査 (tsc), oxlint (警告も誤り), Prettier にかけて, 終わったら消す (写したアプリで初めて誤りが見つかると, 5 つのアプリに同じ直しが要るため)

## 10. 通しの確かめ

殻の通しの確かめは Playwright の e2e (`frontend/e2e`) で, `e2e/serve.sh` が作業用の置き場 (`frontend/e2e/.work`) で殻を起動して行う. 各アプリのテストは単独の起動を確かめ, ここでは殻に載せた後の段階をまたぐ受け渡しを確かめる (どのアプリのテストも, 選んだ問題, 書き出したデータセット, 学習したモデルの受け渡しを見ないため).

| ファイル | 範囲 | CI のジョブ |
| --- | --- | --- |
| `studio.spec.ts` | 殻の画面の動き (段階の並び, 問題の欄, 段階ごとのチャンク, 読めない段階の出し方, 殻の明暗) と, 殻で選んだ問題を各段階の画面が受け取ること. 各段階を開いた所で, 画面の `h1` が 1 つで, 段階の頭の画面では段階の名前, 下の画面ではパンくずの頭が段階の名前のリンクであること (R12 の見出しを殻で守るため). 学習・評価の段階で, ブラウザの戻ると進むが段階の中の移動と段階をまたぐ移動の両方で効き, 作り直した段階の画面が今の経路を読むこと, 殻の欄で問題を選んだままでも段階をまたいで戻ると作り直した画面が今の経路 (`/train/jobs`) を保ち, 進む先の履歴も残ること (殻の選びに合わせる見張りが一覧に移すと, 戻った画面と進む先が消えるため), 問題の設定の段階と往復しても window の popstate の見張りの数が最初に開いたときと等しいこと (外した段階の画面のルーターが見張りを残すと, 見え方は変わらないまま見張りだけが増え, 付け直しを欠くと戻ると進むが効かなくなるため. 殻とルーターの見張りは決まった数なので等しさで比べる). モデルの作成・選定の段階で, 殻の上の帯に focus があるときのキー (消す, 元に戻す) で段階の中身が変わらないこと (R9) と, 書きかけのまま段階を移って戻ると下書きから戻せること, 書きかけのまま殻の欄で問題を替えて戻すと, 少し待って書く分を待たずに読み込み直しても下書きから戻せること (R10) | `e2e` (project `studio`) |
| `journey.spec.ts` | 小さな見本で 5 つの段階を通す. 問題の設定 (見本の「解約の引き止め」を開き, 手元の小さな表を入れ, 学習のプロジェクトを書き出す) → データの分析 (殻で選んだ問題から始め, 記録した場所へデータセットを書き出す) → モデルの作成・選定 (記録からデータセットと保存先が入り, 入力と出力を作って学習のプロジェクトに保存する) → 学習・評価 (記録した学習のプロジェクトを登録し, 1 エポックだけ学習し, ジョブの画面が推論の一式を書き出した後の「完了」を出すのを待つ) → 推論 (殻で選んだ問題の実験から一式を登録し, 元のデータセットのテスト用の分割を選んで推論する. 段階の並びで一式の一覧に戻り, 登録した一式が殻で選んだ問題で絞った一覧に出ること (表の行は見出しと一式の 2 つ), 殻の欄で「選んでいない」にすると推論の段階に留まったまま絞りの印が消えても一式が出ること, 選んだ問題に戻すと絞りに戻ることを確かめる. さらに問題の設定の段階で 2 つ目の問題を作り (殻の欄はその問題を採る), 推論の段階で一覧から登録した一式が消えて「選んだ問題の一式がありません」の文が出ること, 殻の欄で元の問題に戻すと推論の段階に留まったまま一式が出て表の行が 2 つに戻ることを確かめる) | `journey` (project `journey`) |

- 段階の間で値やファイルを手で写さない. 次の段階は殻で選んだ問題と, その `problem.yaml` に記録した場所から前の段階の結果を読む (段階の間の受け渡しを, 利用者と同じ道で確かめるため). テストが決めるのは, 問題に入れる手元のデータと学習のプロジェクトの書き出し先の 2 つの場所だけ (どちらも段階の外から来る値のため). 推論するデータは, 学習に使ったデータセットのテスト用の分割を推論の段階の画面で選ぶ (場所は推論の段階が一式の実験から見つける)
- 学習の終わりは, ジョブの画面の状態の印が「完了」になるのを待つ (推論の段階が実験の一覧に一式を出すのは, 学習の後の処理で一式を書き出した後のため). 印は役割 img と「状態: 完了」などの名前で選ぶ (「後の処理中」の説明文にも「完了」の語が入り, 文で合わせると別の要素を見るため). 「失敗」か「中断」になったら, ジョブの画面の文を付けてすぐ落とす
- 要素は役割と, 欄や region や group の名前で選び, 見出しで section を絞ったり `first()` で選んだりしない (同じ文が他に出たときに, 別の要素を見て通らないため). データの分析の段階と学習・評価の段階の「選んだ問題」の欄は見出しの名前の region で選ぶ. 学習・評価の段階のその欄の中の「記録したプロジェクト」の場所は, 欄の中の group の名前で選ぶ
- 学習は殻の Python (`backend/.venv`) で動く (学習のプロジェクトの上に `.venv` が無いため). 学習の環境を作る操作はしない (依存を網から取って重くなるため)
- 通しの確かめは学習を含んで重いので, Playwright の project で分け (`journey` は `journey.spec.ts`, `studio` はそれ以外の全て), CI では別のジョブにして並べて動かす (後から足した e2e も, 名前を書き足さずにどちらかのジョブで流れるようにするため)
- 殻の置き場は起動のときに 1 度だけ消すので, 置き場の中身はやり直し (CI の retries) と繰り返し (`--repeat-each`) の間で残る. どの e2e も, 前の回の結果が残っていても同じに通るように書く (1 回目が他の理由で落ちたときに, やり直しが効くようにするため). 通しの確かめはやり直しと繰り返しごとに別の場所に書き出す (前の書き出しや登録が残ると, 上書きの確かめで止まるため). 殻の画面の確かめは, 名前で数えたり選んだりする問題の名前にやり直しと繰り返しの印を付け, 2 回目に結果の変わる操作 (データの分析の段階の見本を入れる操作は, 登録済みの見本を登録し直さず「登録済み」と出す) は, 置き場が新しいと確かな最初の回 (やり直しでも繰り返しでもない回) だけ 1 回目の結果を求め (登録できたのに空を返す誤りを拾うため), それ以外の回はどちらの結果も受ける. どの回でも後の状態 (見本が 1 つずつ並ぶこと) を確かめる. 想定しない確かめの窓が出たら誤りとして落とす
